# Per-project recovery tutorials

Each supported title needs its own reproducible tutorial. The common NES Forge guide explains the editors and architecture; a title tutorial explains that game's revision, storage formats, bank context, editable fields and rebuild method. Importing a title does not establish support for every asset or a complete game.

This documentation requirement applies to subsequent recovery checkpoints. It does not retroactively certify older adapters. The current worked title is Punch-Out. Earlier titles have the starting workflows and evidence listed below; expanding them into full lessons remains recorded work.

## Read in this order

1. Read the [developer and asset workflow guide](../NATIVE_RECOVERY_TUTORIAL.md) for the full asset map, independent RE, 6502, external hex editing and HTML changes.
2. Read the title's own tutorial. [Punch-Out](PUNCH_OUT.md) is the current worked example, with separate native editing, source-reference and standalone authoring paths.
3. Use the [tutorial template](PROJECT_TUTORIAL_TEMPLATE.md) when adding another title or revising an existing one.
4. Consult the title's verification reports and repeat the relevant workflow on your own input. Checkpoint evidence is dated; it is not evidence for a later changed application.

`PROJECT_HANDBOOK.html` in the parent documentation directory combines these lessons and the general guide into one offline reading file. The HTML is documentation. The NES Forge application remains a separate standalone HTML, saved projects are separate JSON files, and generated games are separate `.nes` files.

To regenerate the reading file from the repository root, run `python3 app/tools/render_project_tutorials.py` with the Python `markdown2` package available. This optional documentation dependency is not part of the application runtime. The renderer embeds the existing title notes and the full synthetic codec source; it does not embed game assets.

## What every title tutorial must deliver

- A beginner lesson: open the exact input, find the actual scene/area, make one declared supported edit, Undo/Redo, save/reopen, rebuild, reimport and inspect it in the original engine.
- A complete asset inventory with per-domain status: decoded, materialized, editable, native writer, verified context and remaining gaps. Cover graphics, palettes, placement, animation, actors, collisions, menus/text, Worlds/links, code, Audio and samples even when unsupported.
- A format lesson: bank/address-to-file mapping, pointer and compression rules, palette/raster state, source aliases, byte ownership and storage limits. Use a synthetic exercise when teaching data that should not be distributed.
- Independent workflows: do RE and write code without Forge, patch a copied ROM in a hex editor, and inspect/reimport the result. Show a worked expected-byte patch only after its exact revision and consumers are known.
- An application lesson: the decoder → projection → ProjectStore → editor → native writer connections; exact modules/HTML markers; how to bundle a customized standalone HTML.
- A separate authored-game lesson: bring supported material into a new project, create missing behavior explicitly, build a standalone ROM and test it outside Forge. State the current conversion gaps.
- Audio verification, original-engine checks, reproducible commands and an owner checklist. Automated checks never silently check listening, playability, controller or hardware boxes.

A title checkpoint is documentation-complete only for its declared scope when someone can reproduce its lesson from the named application and exact input. Open fields remain open. Expanding a title's scope requires updating its tutorial in the same checkpoint.
