Title methods and tutorial requirements

Per-project recovery tutorials

Each supported title needs its own reproducible tutorial. The common NES Forge guide explains the editors and architecture; a title tutorial explains that game's revision, storage formats, bank context, editable fields and rebuild method. Importing a title does not establish support for every asset or a complete game.

This documentation requirement applies to subsequent recovery checkpoints. It does not retroactively certify older adapters. The current worked title is Punch-Out. Earlier titles have the starting workflows and evidence listed below; expanding them into full lessons remains recorded work.

Read in this order

  1. Read the developer and asset workflow guide for the full asset map, independent RE, 6502, external hex editing and HTML changes.
  2. Read the title's own tutorial. Punch-Out is the current worked example, with separate native editing, source-reference and standalone authoring paths.
  3. Use the tutorial template when adding another title or revising an existing one.
  4. Consult the title's verification reports and repeat the relevant workflow on your own input. Checkpoint evidence is dated; it is not evidence for a later changed application.

PROJECT_HANDBOOK.html in the parent documentation directory combines these lessons and the general guide into one offline reading file. The HTML is documentation. The NES Forge application remains a separate standalone HTML, saved projects are separate JSON files, and generated games are separate .nes files.

To regenerate the reading file from the repository root, run python3 app/tools/render_project_tutorials.py with the Python markdown2 package available. This optional documentation dependency is not part of the application runtime. The renderer embeds the existing title notes and the full synthetic codec source; it does not embed game assets.

What every title tutorial must deliver

  • A beginner lesson: open the exact input, find the actual scene/area, make one declared supported edit, Undo/Redo, save/reopen, rebuild, reimport and inspect it in the original engine.
  • A complete asset inventory with per-domain status: decoded, materialized, editable, native writer, verified context and remaining gaps. Cover graphics, palettes, placement, animation, actors, collisions, menus/text, Worlds/links, code, Audio and samples even when unsupported.
  • A format lesson: bank/address-to-file mapping, pointer and compression rules, palette/raster state, source aliases, byte ownership and storage limits. Use a synthetic exercise when teaching data that should not be distributed.
  • Independent workflows: do RE and write code without Forge, patch a copied ROM in a hex editor, and inspect/reimport the result. Show a worked expected-byte patch only after its exact revision and consumers are known.
  • An application lesson: the decoder → projection → ProjectStore → editor → native writer connections; exact modules/HTML markers; how to bundle a customized standalone HTML.
  • A separate authored-game lesson: bring supported material into a new project, create missing behavior explicitly, build a standalone ROM and test it outside Forge. State the current conversion gaps.
  • Audio verification, original-engine checks, reproducible commands and an owner checklist. Automated checks never silently check listening, playability, controller or hardware boxes.

A title checkpoint is documentation-complete only for its declared scope when someone can reproduce its lesson from the named application and exact input. Open fields remain open. Expanding a title's scope requires updating its tutorial in the same checkpoint.

Punch-Out worked tutorial

Punch-Out: import, edit, rebuild and understand the method

This lesson covers the current Mike Tyson's Punch-Out!! US PRG0/PRG1 support. You will make a supported arena edit, preserve it in a project, build a separate ROM, inspect fighter/player/referee references, audition source Audio and find the code needed to extend the method. The bounded original-engine replay, reversible knockdown/round experiments and dedicated physical CHR/fight-palette writers extend that workflow. Complete fights, native pose/animation and Audio writers remain open.

The combined review application is NES_Forge_Retro_Punch_Out_Native_Workflows.html, identical to app/mainline/NES_Forge_2.0.0-alpha.11.html. Its SHA-256 is cf5825b600fc8f8c028e9df0def70cc1cac483408ad49b8327715b02a4598e08. Sections 13–15 describe the new dedicated artwork, original-engine replay and Retro Workstation controls. The preceding verified fight-reference checkpoint remains separately available at local commit e2d94cb (app SHA-256 aceb8cdd70e0839b4649bc56daa39519204b660bbbae100209ad9e66bb03b89a).

2. First lesson: change the shared arena

  1. Open the current application in a browser. Save any current work. Choose Open ROM / project, choose your supported original, Prepare recovered resources (partial), then Import as new project. If you already have a saved recovered project, open that JSON instead.
  2. Open Recovered content → Open ring and audience. Select Arena · ring and audience · source setup. This is assembled placement, not a raw pattern sheet. Fighter-source Scenes can intentionally have blank backgrounds.
  3. Before editing, use Build & Run and retain a baseline output. An unchanged native build must preserve the input exactly. The original game starts; the source Scene is an editing view, not a replacement reset screen.
  4. In the arena Scene, choose an existing tile and change one ordinary ring/audience cell using the Scene tools. Use a small change that is easy to recognize. Record its zero-based column/row and original/new native tile IDs. Avoid $FD/$FE in the beginner exercise: pattern reads of those tiles control graphics-bank latches. Keep the other asset fields unchanged.
  5. Test Undo, then Redo. Use Check arena build. The writer supports layout tile IDs and visible attribute palette IDs. Changing an attribute chooses a palette group; it does not change the four actual NES color values.
  6. Use Save Project As. Close/reopen the JSON in a fresh application instance and confirm the intended arena edit. Use Build & Run and download the built ROM through the existing build controls.
  7. Enter a fight in the original game and inspect the shared arena. HUD/player updates can overwrite cells; choose a stable ring/audience location and inspect multiple rows. Check that Audio remains present. External emulator play is a separate useful acceptance check.
  8. Reopen the rebuilt ROM through Open ROM / project and prepare/import again. Supported arena derivatives should retain recognition, the arena edit, recovered source content and the Audio catalog. Preserve the project JSON as the richer editing record.

If the writer reports a capacity failure, simplify the pattern or Undo. Nothing should be silently dropped. A successful native build does not prove the edit preserves a playable fight or every later state.

4. Staging backgrounds and source aliases

Use Area library → Investigated source to select an available staging context/page. The native block controls project a narrow physical-literal recipe. Choose the native block ID and cell through NATIVE SCREEN BLOCKS or its canvas brush. Ordinary unrestricted Scene painting is not a substitute for a recipe-owned staging edit.

These five contexts come from declared combinations of source programs; 84 available command programs are decoded out of 95 table slots. There are 711 writable bytes in 97 spans per revision. A repeat operand can supply many displayed cells, and several contexts can share it. The native owner updates those aliases together. Refusal for inherited/generated cells or metadata aliases protects source semantics.

Repeat the same Undo/Redo → save/reopen → build → original-engine → derivative-reimport exercise. Check the other affected contexts. Do not interpret the five staging views as five complete fights or all game menus.

5. Fighter poses and observed opponent animation

  1. Open Recovered content. Choose Fighter / fight and Pose. Inspect the source bank, palette offsets and pointer evidence. The preview is centered for inspection; that centering does not change native placement and does not simulate hardware scanline clipping.
  2. Choose Open pose in Metasprites to materialize that supported source pose, or Recover background pages and fighter samples for the bounded overview. It uses existing Scenes/metasprites and one Undo transaction. It does not replace the source ROM.
  3. Expand State animation excerpts. Select a source state and a bounded Native updates window, then Trace state. Inspect observed frames, duration and sprite-size changes. Some entries require context and can refuse an isolated pose while a valid preceding trace establishes it.
  4. Choose Open recovered animation to add the canonical excerpt. Save/reopen and inspect Animation/Metasprites. Inspect linked sound opens observed source Audio requests; those requests are not automatically authored runtime events.
  5. Save animation/art experiments separately. Editing them is useful, but native rebuilding requires undoing unsupported changes or returning to a saved native-buildable baseline. Reopening a copied animation does not create a missing native writer.

Use Browse all CHR banks for physical patterns. Tile patterns, assembled poses and timed state execution answer different questions. The game changes sprite size and CHR context, so decoding each shape as an independent static picture can produce the wrong result.

6. Mac, referee and HUD composition

  1. In Recovered content, expand Glass Joe fight reference · Little Mac / referee / HUD.
  2. Start with Mac command 0, referee command 144 and Glass Joe source pose 0; choose Preview pose composition. It uses original setup health/hearts/stars/score/clock routines. The opponent is at the original configuration's upper-right opening position; this is a declared setup reference.
  3. Change a Little Mac command or Referee / speech command, then preview again. Commands can update only a fragment, clear cells or change speech/count data. Do not expect every entry to be a full self-contained character.
  4. Choose Native player state, set Native updates from 1 to 600 and choose Trace player / referee state. Select an Observed excerpt frame. The 23 available entries trace a declared zero-input path. update-limit means observation stopped at the budget; other game systems or input may be needed to progress.
  5. Choose Open selected fight reference. This adds an ordinary Scene with separate opponent OAM and bank/scroll/raster provenance in one Undo transaction. Save/reopen it. It is labeled as a recovered source reference, not verified runtime capture.
  6. Choose Edit native arena layout to return to the actual arena write owner. Paint there, then preview again: the composition uses the current encoded arena when native building succeeds. If unsupported work blocks building, inspection can explicitly fall back to preserved source plus existing literal recipes; read its warning.

Editing the reference's own CHR, palettes, sprites or background remains savable and blocks native building. Such work cannot be silently re-signed as unchanged source. Preview guards also reject materialization when the project changed after preview; preview again after a legitimate edit.

The trace updates source state then uploads its command immediately. It does not reproduce original NMI arbitration, concurrent opponent AI, damage or complete fight phases. Fine scroll and MMC2 reads remain modeled rather than flattened into an ordinary tile grid.

7. Audio, including the startup sample

  1. Choose Open source Audio, or AUDIO → ROM Audio Library after import/reopen. Check that the source profile matches your revision. There are 84 entries, including six empty slots and two stop controls; a catalog entry is not always a sounding cue.
  2. Select music or an effect; choose Inspect cue, then Play native. Stop playback before another experiment. The bank-8 driver supplies 23 sounding music selections, 45 procedural effects and seven DPCM selections.
  3. Select Startup PCM + native bell and use at least 199 native updates for the full isolated routine. Shorter windows report truncation. This separate bank-6 routine produces direct DAC writes; it is not ordinary tracker music.
  4. For representable music/effects, choose Preview editable score, review the declared losses, then explicitly import into the tracker. Check Undo/Redo and save/reopen. A music import changes the canonical order/tempo; preserve a separate experiment if you want to continue native arena building.
  5. Undo an unsupported Audio import before the next native build. Reopen the arena derivative and check its native Audio catalog/audition again. Source sample bytes and original driver code should remain preserved.

The native machine executes original timing/driver requests in a repeatable isolated context. Tracker conversion is finite and frame-sampled; DPCM and short-mode noise can be omitted or conversion refused. It does not recover complete song loop structure, native instruments or game event routing. Automated APU/PCM checks do not establish browser listening quality.

8. How this particular format works

This investigated iNES layout has a 16-byte header, 128 KiB PRG and 128 KiB CHR. MMC2 selects PRG/CHR banks; a CPU address is not a unique file offset. For a declared 8 KiB PRG bank mapped at $8000–$9FFF, the physical offset is 16 + bank * 8192 + (cpuAddress - $8000). Fixed windows need their actual selected physical bank too.

The arena writer owns four two-byte pointers in physical bank 12 at CPU addresses $917B, $917E, $9184, $9187, plus 381 bytes at $9190–$930C. Their file offsets are respectively $1918B, $1918E, $19194, $19197, and the storage range is $191A0–$1931C. End addresses here are inclusive. These are exact-source arena ownership ranges, not general free space.

The writer starts from original raw nametables, maps visible cells across the scroll seam through cellSources, updates visible attributes, compresses each page into at most two source streams, and updates the owned pointers. It refuses total-capacity or per-stream overflow and decodes the candidate with the original loader. Offscreen cells and unrelated code/CHR/Audio stay protected.

The native literal brush instead owns individual source operands. Its writer is not interchangeable with the arena compressor. Both flow through NativeResourceProject and the existing native backend.

MMC2 switches CHR during pattern-address reads. A tile outside the visible viewport can select the bank for a subsequent row. Rendering retains 34 background fetches per scanline; clipping pixels cannot remove those reads. Mac and referee use bank-11 nametable commands, while opponent poses use OAM/shape routines. These differences explain the separate recovery modules.

9. Independent RE, code and hex editing

You can investigate without using the recovery buttons. Hash a copied original; record its bank map; disassemble a declared bank at its CPU origin; follow native pointer consumers; record inputs, RAM changes, PPU/OAM writes and sound requests. Keep notes about starting state and stop conditions. General analysis is read-only; reversible RAM experiments affect an emulator session rather than the ROM.

As a read-only source exercise, run Node from the repository root. Save the following as inspect-punch-out.cjs there and pass your own original path. It writes only summaries to the terminal:

const fs = require('node:fs');
const crypto = require('node:crypto');
const bytes = new Uint8Array(fs.readFileSync(process.argv[2]));
const hash = crypto.createHash('sha256').update(bytes).digest('hex');
const formats = require('./app/src/re/native-punch-out-resources.js');
const profile = formats.profiles.find(p => p.kind === 'punch-out' && p.sha256 === hash);
if (!profile) throw Error('Use an investigated original for this exercise.');
const content = require('./app/src/re/punch-out-content.js').open(bytes);
const arena = require('./app/src/re/punch-out-arena.js').open(bytes);
const fight = require('./app/src/re/punch-out-fight.js').open(bytes);
console.log({profile: profile.id, fights: content.fights.length,
  arenaCells: arena.nt.length, commands: fight.poses.length,
  availablePlayerStates: fight.states.filter(s => s.available).length});

node inspect-punch-out.cjs /path/to/original.nes
node app/docs/native-codec-exercise.cjs

Expected current counts are 14 fight configurations, 960 arena cells, 145 combined Mac/referee command descriptors and 23 available state entries. The second command teaches decode → edit → encode → reopen → reimport using a deliberately synthetic format. Its bytes are not Punch-Out command bytes.

For external hex work, use the mapped offsets above to inspect arena pointers and compare an app-built candidate with the exact original. Verify every changed byte falls within the declared owners for the edit you made. Those compressed bytes do not have one visual-cell-to-byte correspondence; a layout edit can change stream lengths and pointer values. Do not type a tile number into a guessed compressed offset.

For your own supported arena encoder, follow PunchOutArenaEncoder.encode(bytes, {nt, attr}) and its spans/capacity contract on a copy, then validate with the independent original-loader checks. The service adds project-signature, alias and unsupported-field checks beyond this low-level helper. Using the helper alone is not complete project build validation.

For a code patch, identify its callers, native bank, CPU origin, owned space, vectors, stack/RAM effects and timing; assemble externally or through the supported assembler into a separate patched ROM. Verify exact expected original bytes and all changed ranges. CODE text in a preserved native project is not automatically injected. Changes outside admitted native ranges can lose specialized recognition and still be inspectable through general RE.

11. Build a separate standalone game

There are three distinct outcomes. The preceding native lesson produces a standalone .nes using the preserved original engine. The HTML lesson produces a customized standalone NES Forge application. Creating a new original game is an authored-project workflow with its own behavior and build backend.

For that new game, start a separate authored project and save it immediately. Create original or otherwise usable art; explicitly import only supported asset types through existing tools, or recreate a small asset with the editors. Select the appropriate Scene/CHR/palettes, assemble metasprites/animation, add the supported actor/behavior or custom assembly, then author collision, state transitions, Audio and persistence deliberately. Preserve referenced IDs and test the chosen runtime's compiled subset.

Recovered Mac/referee raster commands do not currently convert into a complete playable authored boxing actor. No one-click whole-Punch-Out conversion exists. Do not delete the native descriptor from a recovered JSON and assume all source relationships become authored behavior. Keep the native source project as a reference and maintain the authored project separately.

2. Understand the three representations

  1. Source: importedRom preserves the input bytes. In project JSON it is Base64; the live editor holds bytes. nativeGame.sourceSha256 identifies those bytes. Never edit one without updating and validating the complete source descriptor and associated evidence.
  2. Evidence: investigation and decoder catalogs describe observations, source ranges, profiles and gaps. They are not a second asset database or executable game source. Viewing a catalog does not mean every item has been materialized into an editing tab.
  3. Canonical authoring assets: scenes, worlds, metasprites, animations, Audio collections and gameplay records are the editable project. Some are linked to native recipes; others are recovered copies or adaptations with no inverse writer.

A useful recovery must state separately: recognized, decoded, materialized, editable, natively encodable, and verified in play. A source can be recognized without complete assets. 4. Visual asset editing, end to end

Backgrounds, tiles and palettes

  1. Save a baseline project. Select the actual target Scene or source page. A fighter-source Scene intentionally has a blank background; an intro Scene is not the fight arena.
  2. Inspect its CHR and palette. If source graphics are banked, record physical bank and runtime latch/scroll context. Do not replace missing placement data with a tile sheet and call it a recovered scene.
  3. Paint the Scene layout, or edit CHR pixels deliberately. Palette-ID painting changes attributes; the color picker changes palette colors. These require different native writers.
  4. For a native project, check the declared supported fields. Punch-Out arena nt/visible attribute edits are encodable. For native artwork/color edits, open the dedicated physical CHR or fight-palette views described in section 15; direct edits to copied arena/fight-reference art remain unsupported. Unsupported edits remain savable but block native builds.
  5. Undo, Redo, save, reopen and rebuild. Enter the game state that uses the data. Test neighboring rows, page seams, offscreen dependencies and shared uses.
  6. Re-import the rebuilt ROM if continuing from it. This checkpoint restores Punch-Out recognition for bounded arena derivatives; arbitrary patches outside recognized ranges still need adapter investigation.

Background CHR pixel 0 is the background color selection; sprite pixel 0 is transparent. Sprite/background palettes and bank selection are separate. Some projected source Scenes can use more than 256 logical tiles to preserve bank-dependent rows; those logical indices cannot be written directly to an 8-bit native tile stream.

Sprites, metasprites and animation

Open Recovered content for source poses or the regular editors for authored work. Select fight/pose, preview, then explicitly open a supported pose in Metasprites. Verify the pose's source Scene, sprite size, origin, piece order, flips, palette and CHR bank.

For timed source recovery: State animation excerpts → Trace state → Open recovered animation. Inspect assumptions and stop conditions. Frames changing size must retain the native tile stride; incremental poses must retain the preceding OAM. Adjust canonical frame timing or pieces, preview, save and reopen. This does not yet encode those changes into Punch-Out's original animation streams.

When creating authored animation, keep stable metasprite IDs, reference their Scenes, set duration/loop behavior and bind entity states to animation IDs. Test hitboxes, hurtboxes and events in the intended runtime; the editor preview alone does not establish compiled behavior. Do not delete a referenced Scene or pose to make room without reviewing the references reported by AssetRegistry.

Worlds, collision, actors and interactions

For an authored World, establish the tileset Scene and metatile library before painting its map. Define rooms, markers, destinations and camera regions; test travel in both directions and after room reload. Enable the intended World/runtime settings. A saved marker is not evidence that a native game's original travel code uses it.

For authored collision, choose properties based on intended mechanics, then test actor movement/contact. Verify per-cell overrides and metatile projection where applicable. For actors, distinguish a reusable definition from placed instances. Keep variables typed and scoped, use only operations supported by the compiled backend, and test deterministic transition priority, spawn/despawn, slot reuse and persistence across rooms. Refer to GameplayModel.runtimeProfile for the bounded native runtime subset rather than assuming every UI operation is compiled.

For native projects, recover these domains from original tables/code independently. Tile appearance, pose geometry and enemy labels cannot establish physics, damage, AI or save-state semantics.

Audio

On every project verify driver detection, cue inventory, native audition, explicit editable conversion where supported, save/reopen and preservation after Scene rebuilding. Empty/stop/unavailable cue slots should be labeled rather than counted as sounding music.

Native audition runs original driver code with native sample sources. Tracker conversion makes finite canonical patterns/instruments where representable; listen for differences in envelopes, pitch slides, channel ownership, noise, loops and DPCM. Save the project, reopen, audition again and compare Scene-edited output. Audio writing requires its own native encoder.

5. Manual RE workflow

  1. Identify the input. Record size, full hash, header, trainer/trailing data and physical PRG/CHR layout. Preserve the input unchanged. A legacy header can disagree with observed bank-switching code; keep the disagreement explicit.
  2. Choose an explicit range. General analysis accepts physical file offsets, length, CPU origin when known, and bank labels. File offset and CPU address are not interchangeable.
  3. Separate code from data. Linear disassembly is a hypothesis. Check reset/NMI/IRQ vectors, reachable calls, indirect pointers, bank changes and data reads. Label uncertain ranges.
  4. Find consumers. Trace PPU writes for backgrounds/palettes, OAM construction for sprites, APU writes for sound and RAM/state routines for behavior. The code consuming a record establishes its meaning.
  5. Make a reproducible observation. Save an emulator checkpoint, replay scripted input or apply a reversible RAM experiment. Record starting state and stopping condition. Runtime experiments do not patch the ROM or authored project.
  6. Retain evidence. Record bank + CPU address + physical offset, operand width/endian order, bounds, aliases, decoded meaning and unknown context. Export notes/report separately from project changes.
  7. Implement only an established claim. A private decoder can return a read-only catalog before any visual import or writer exists. Unknown sources remain inspectable without a guessed adapter.

For 8 KiB banks in a standard header/no-trainer example:

fileOffset = 16 + physicalBank * 8192 + (cpuAddress - windowStart)

This formula requires a known mapped window. A trainer changes the payload start; NES 2.0 and other layouts need their actual container description. Read the container/layout owner instead of hard-coding 16 for an arbitrary game.

6. Worked native codec lesson

Run the included exercise with Node:

node app/docs/native-codec-exercise.cjs

It defines an original teaching format, not a commercial ROM. A header points to fixed-capacity [count, tile] RLE data describing eight cells. Read its decode, encode and exercise functions in order.

The exercise demonstrates: strict bounds; a canonical grid; edits on a detached copy; run compression; capacity refusal; preservation of unrelated bytes; decoding the candidate; JSON save/reopen; and byte-identical unchanged derivative output. Extend it by adding a second shared view, then ensure editing a shared operand updates both views. Next add attributes as a separate record and reject mismatched ownership spans.

In Punch-Out, the method becomes:

  1. punch-out-layout.js independently interprets native PPU commands and records which output cells share literal operands.
  2. native-punch-out-resources.js projects static backgrounds while retaining actual CHR-latch row context. The physical operand, not each visible cell, owns a native literal recipe.
  3. punch-out-arena.js executes the original setup loader on a private bus, recovers two raw nametables, then projects a viewport using NT1 and scroll $B0.
  4. Each visible cell retains cellSources: its source nametable and native cell. This is the inverse map required by the writer.
  5. punch-out-arena-encoder.js copies raw pages, applies supported tile/attribute changes back through that map, compresses into four streams, and stays inside the original 381-byte area plus four pointer words.
  6. The encoder executes the original loader again on the candidate and compares all raw pages and the visible projection. Oversized or unrepresentable edits refuse with a useful error.
  7. punch-out-arena-writer.js registers the encoder with the existing native build owner. It masks only nt/attr during projection-signature validation; CHR, colors, actors and unrelated settings remain protected.
  8. The shared native owner composes literal recipes with arena writes, rejects overlapping claims, checks every changed byte and returns an artifact to the existing RuntimeCompiler.

The compressor searches native literal, repeat, increment and repeated-sequence operations. Each page has two streams indexed by an 8-bit Y register: command bytes plus a terminating zero must fit before wrap. Minimal encoded byte cost and successful stream partitioning are different requirements; both must be checked. No general relocation/expansion is implemented.

The 2026-10-24 derivative correction adds a separate immutable identity for those supported arena write ranges. Recognition may ignore only declared mutable data and must still decode bounded valid programs. This does not grant the literal brush ownership of the arena. Current stream pointers must stay in the owned area, terminate without Y wrap and initialize exactly both pages. Changes to header, code, Audio or CHR remain outside that identity.

8. Writing 6502 code yourself

Use a separate authored project for custom assembly. Save the native recovery project first. In CODE choose the Minimal boot ROM or Scene viewer template; inspect the code before replacing any existing source. Use Assemble / Ctrl+Enter and review errors, symbols, origin and emitted bytes.

The assembler supports the implemented syntax including labels, .org, .byte, .word and supported instructions/addressing modes. Consult asm_assemble for exact syntax. Overlapping addresses, out-of-range branches and unresolved operands must be fixed before output.

A minimal boot template intentionally shows no graphics: it disables rendering, establishes a stack and loops, with reset/NMI/IRQ vectors. Add PPU initialization, graphics upload, NMI updates and controls deliberately. Use a complete live custom project build and test the emitted reset path.

BuildGraph.backendFor selects native-engine when a preserved native descriptor is present. Writing text into CODE does not turn that descriptor into a safe arbitrary native code patch. For authored custom output, use the matching viewer/custom settings; packScenes=false plus assembly and no conflicting gameplay/World mode selects unpacked custom output. Runtime Audio cannot be automatically injected into custom assembly. Detached compilation cannot invoke the live assembler.

For editing an existing game's code, assemble the replacement with your toolchain or the supported assembler, map CPU writes into the correct physical bank, reserve/verify owned space, and produce a separate patched ROM. Recover relocations, callers, vectors and timing as needed. Re-import for inspection; adding native adapter recognition/build support is a separate step. A disassembly listing alone is not complete linkable source.

9. Hex editing yourself

Create a copy and record the exact original hash. Locate the physical offset using the active bank and container layout; verify expected original bytes before a patch. Change one field, export a distinct ROM and compare all changed ranges. Preserve your patch recipe separately so it can be reapplied and reviewed.

For a one-byte observation, check every consumer: compressed operands can expand into many cells; pointers can be little-endian and bank-relative; palette bits can affect four neighboring tiles; CHR patterns can be shared across unrelated Scenes. A value used as both graphics and a latch control has runtime side effects.

Reopen the patched ROM in general analysis regardless of whether a specialized adapter recognizes it. If a protected code/CHR/Audio byte changed, the adapter may correctly stop recognizing the derivative. To support it as an editable native project, establish its new identity, verify its structures and add bounded writer support. Do not relax detection to a filename, mapper number or broad checksum mask.

For RAM hypotheses use the reversible experiment controls: checkpoint, apply, replay, restore or keep. Keeping changes only that emulator session. To make the behavior persistent, identify and patch the native initialization/update code or save format separately.

The read-only analysis pane, reversible RAM editor, narrow native command editor and external hex editor remain complementary workflows. None should silently replace or modify the current saved project.

Runnable synthetic exercise

Synthetic codec source

Save this as native-codec-exercise.cjs and run node native-codec-exercise.cjs. This is an invented 48-byte teaching format, not an NES ROM or a Punch-Out decoder.

'use strict';
// Synthetic teaching format, authored for this tutorial. This is NOT an NES
// game decoder or evidence that any commercial title is supported.
const assert = require('node:assert/strict');

// File layout: 16-byte header, 16-byte RLE storage, 16 protected sentinel bytes.
// Header [0..3] identifies this format; [4..5] is a little-endian data pointer.
// Each stream pair is [count, tile], with count=0 terminating the stream.
const DATA = 16, CAPACITY = 16, CELLS = 8;
function decode(rom) {
  assert.equal(rom.length, 48);
  assert.deepEqual([...rom.slice(0, 4)], [0x4e, 0x46, 0x45, 1]);
  const start = rom[4] | rom[5] << 8;
  assert.equal(start, DATA);
  const cells = [];
  let ended = false;
  for (let p = start; p < DATA + CAPACITY;) {
    const count = rom[p++];
    if (!count) { ended = true; break; }
    assert(p < DATA + CAPACITY, 'Missing RLE operand');
    const tile = rom[p++];
    assert(cells.length + count <= CELLS, 'RLE overrun');
    cells.push(...Array(count).fill(tile));
  }
  assert(ended && cells.length === CELLS, 'Missing terminator or incomplete room');
  return {width: 4, height: 2, cells};
}
function encode(source, room) {
  decode(source); // Validate the source before deriving a new candidate.
  assert.equal(room.cells.length, CELLS);
  assert(room.cells.every(n => Number.isInteger(n) && n >= 0 && n <= 255));
  const stream = [];
  for (let i = 0; i < CELLS;) {
    let count = 1;
    while (i + count < CELLS && room.cells[i + count] === room.cells[i]) count++;
    stream.push(count, room.cells[i]);
    i += count;
  }
  stream.push(0);
  assert(stream.length <= CAPACITY, 'Fixed native storage capacity exceeded');
  const candidate = source.slice();
  candidate.set(stream, DATA); // Do not rewrite the header or protected bytes.
  assert.deepEqual(decode(candidate).cells, room.cells);
  for (let i = 0; i < source.length; i++) {
    if (i < DATA || i >= DATA + CAPACITY) assert.equal(candidate[i], source[i]);
  }
  return candidate;
}
function exercise() {
  const source = new Uint8Array(48).fill(0xaa);
  source.set([0x4e, 0x46, 0x45, 1, DATA, 0], 0);
  source.fill(0, DATA, DATA + CAPACITY);
  source.set([4, 1, 4, 2, 0], DATA);
  const frozen = source.slice();
  const room = decode(source);
  assert.deepEqual(room.cells, [1, 1, 1, 1, 2, 2, 2, 2]);
  room.cells[1] = 3;
  const built = encode(source, room);
  assert.deepEqual(decode(built), room);
  assert.deepEqual(source, frozen, 'The source must remain unchanged');
  const saved = JSON.stringify({source: [...source], room});
  const reopened = JSON.parse(saved);
  assert.deepEqual(encode(Uint8Array.from(reopened.source), reopened.room), built);
  assert.deepEqual(encode(built, decode(built)), built, 'Unchanged derivative is byte-identical');
  assert.throws(() => encode(source, {cells: [0, 1, 2, 3, 4, 5, 6, 7]}), /capacity/);
  const invalid = source.slice(); invalid[4] = 47;
  assert.throws(() => decode(invalid));
  console.log('Synthetic codec exercise passed: decode, edit, encode, reopen, re-import, bounds, protected bytes.');
}
if (require.main === module) exercise();
module.exports = {decode, encode, exercise};
