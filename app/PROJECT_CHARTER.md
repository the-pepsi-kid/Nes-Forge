# NES Forge project charter

NES Forge is a visual **NES / 8-bit / 6502-class** game-development, runtime and reverse-engineering environment with optional assembly and existing ROM inspection/capture tools. Ordinary editor controls remain the primary workflow. The distributed application remains one standalone HTML with reproducible source, tools, tests and editable external examples.

## Hard platform identity

The canonical game target is Nintendo Entertainment System / Famicom-class behavior and presentation: Ricoh 2A03/2A07 6502-derived execution, NES PPU concepts, CHR/tiles/metatiles, NES sprites/metasprites and palettes, NES APU-style audio, NES-compatible mapper/runtime profiles, controller concepts and generated 6502-class game logic.

Modern infrastructure may extend authoring, builds, testing, reverse-engineering analysis, Method Registry services, hosting, networking, persistent Worlds, matchmaking, accounts/sessions, collaboration and voice/text communication around the game. It must not replace the NES runtime target with a modern native engine, 3D engine, 16-bit runtime or cosmetic “NES-looking” presentation layer.

NES Forge is not a general-purpose game engine, Unity/Unreal-style client, SNES/65C816 environment or modern GPU scene graph. If a future 16-bit environment is authorized, it must be a separate product such as SNES Forge with its own hardware model, compiler/runtime, memory/mapper model, canonical representations and verification baseline. **NES Forge may become broader around the NES, but not broader instead of the NES.**

## Domain, lifecycle and capability-path rules

NES Forge follows a domain-oriented modular-monolith architecture. CHR/Graphics, Metatiles, World, Metasprites, Animation, Gameplay, Audio, Raster behavior, Reverse Engineering, Method Registry, Hosted Session/Networking, Hosted World persistence, Social/Voice and Collaboration are bounded contexts. Each owns its canonical model, validation, authoring semantics, compilation semantics and domain-specific tests. Cross-domain interaction uses stable IDs, typed references, declared dependencies, versioned contracts, events and explicit adapters; no domain may depend on another domain's private implementation.

Canonical object lifecycles must be explicit. For example, Actor Definition → Actor Instance → compiled representation → Runtime Actor → transient state → explicit Room/World persistent state → despawn/reconstruction. Features are complete only when their end-to-end capability path is proven from authoring/import through validation, compilation, NES runtime and applicable inspection/reimport. Vertical slices may cross domains to prove those paths but must not erase ownership boundaries. BuildGraph coordinates dependencies; it does not own domain semantics.

Networking owns transport and synchronization, not gameplay meaning. Gameplay decides why a Door opens and what that means; Networking may carry the resulting typed event. World owns spatial structure, Audio owns sound semantics, Inventory/Economy/Crafting own their future domain concepts, Hosted persistence owns durable remote storage, and Voice owns communication outside deterministic NES simulation.

## Boundaries

- Preserve all verified 1.7 World behavior and the five pinned legacy ROMs. Audio Runtime starts disabled for supported older projects, so unchanged builds remain byte-identical.
- Keep ProjectStore, BuildGraph/RuntimeCompiler, WorldCompiler/WorldEngine and existing UI/lifecycle owners authoritative. Add audio through explicit AudioConfig, AudioCompiler, AudioEngine, AudioImport and AudioUI boundaries.
- Keep mapper 0, current PRG/CHR profiles, whole-screen World transitions, inactive LiveLink, and existing ROM layout families. Audio capacity must fail explicitly rather than changing mapper or silently dropping data.
- Generated viewer, single-room and World code may host Audio Runtime. Authored custom assembly cannot silently receive generated code and is therefore incompatible while Audio Runtime is enabled.
- Execute two pulse channels, triangle and noise. DPCM samples and tracker effect commands have no 1.8 runtime semantics and must fail when executable.
- MIDI/MusicXML import may quantize into the tracker’s supported voices and one global tempo. Unsupported formats, tempo structure or excess polyphony must be reported. Import does not automatically enable runtime output.
- The 1.9.0 candidate does not include sheet-music/tab transcription, smooth scrolling, new mappers/profiles, release/debug source-embedding modes, automatic editable recovery beyond the D048 supported native-room profile, incremental compilation, hot reload or Live Edit. Each remains in its ordered later milestone or an expressly authorized tranche.
- Do not extend `worldRuntime` with role-specific `enemy1`, `enemy2`, `boss` or similar fields. General gameplay uses the canonical actor/behavior/component architecture.
- Emulator frame history is a temporary analysis/playtesting tool. It does not add authored persistence scopes, exported save states or gameplay snapshot semantics. Keep recording opt-in, enforce bounded serialized storage, clear/reseed on lifecycle changes, and preserve neutral paused navigation.
- Do not wholesale-merge the separate RE branch or distribute third-party game assets. Future RE transfers use explicit evidence and canonical conversions; the Method Registry stores reusable techniques and provenance.
- Preserve lossless raster-dependent captures even when the current static NROM backend refuses to rebuild them. Do not flatten or approximate unsupported effects. Captured, canonically Represented and Compilable-by-profile are separate claims.
- Canonical Raster Events, scrolling/raster runtime profiles, mapper IRQ behavior and timing-sensitive live edits begin with the ordered 2.0 foundation and are explicitly outside 1.9.
- For 1.9, templates are starter recipes, the structured state table is canonical, and any future visual state graph is only a view/editor over that model. Explicit Transient/Actor-local, Room and World scopes separate runtime state from persistent authored variables. Player/Target uses a compatibility adapter first.
- 1.9.0 includes only the core identities/framework/evaluator/persistence/adapter/table/runtime work and five templates: Sideview Player, Ground Patrol Enemy, Stationary Contact Hazard, Collectible Pickup and Switch + Door.
- Projectiles, moving platforms, in-session checkpoints, minimal dialogue, ladders/one-way platforms and richer gameplay wait for separately authorized 1.9.1. The visual graph and improved behavior UX wait for 1.9.2.
- Stop after the tested 1.9.0 candidate and handoff. Do not begin 1.9.1, 1.9.2 or later work without explicit authorization.
- Do not pull future Session, Player, Hosted World or Account persistence scopes into 1.x/2.x. Current Transient, Room and World semantics remain backend-neutral so a later host can reuse them deliberately.
- Future Hosted Worlds may maintain state far beyond one cartridge or console, but each client receives only an interest/proximity-filtered NES-compatible local projection. The NES-class runtime remains the game client.

The 1.9.0 candidate must include reproducible source, schema-12 compatibility evidence, canonical model/compiler/runtime coverage, retained Audio/World/legacy evidence, the independent native-ROM source/builder, supported decoder evidence, an editable recovery workflow, documented limits and a handoff. Navigation completion additionally requires actual machine/APU/capture-state restoration, deterministic forward/branch boundaries, bounded history and safe lifecycle/input handling. Comprehensive RE remains a longer-term program beyond either slice. General ASM/Lua migration remains proposed work, not implemented compatibility. Mock-DOM/emulator evidence remains separate from real-browser, audible-speaker and independent-hardware acceptance. Stop at this candidate for independent audit. 1.9.1 and 1.9.2 remain separately gated.
