# CAD-PORT-01: CadEditor's NES knowledge in Forge's recovery pipeline

Status: batch 1 implemented and tested (shared block, big-block and screen formats; recognition; import-time
integration; verification ledger; coverage). Acceptance: `QA/cad-port-01.cjs`. Related:
[Agent Lab verification](AGENT_LAB_VERIFICATION.md), [licensing review](../licensing/THIRD_PARTY_REVIEW.md).

## What it is, and what it is not

[CadEditor](https://github.com/spiiin/CadEditor) (MIT, Copyright (c) 2018 spiiin) is a level editor whose per-game
configuration files record where many NES games keep their block tables, big-block tables and screens. CAD-PORT-01
translates that knowledge into Forge-native definitions and reusable decoders. It is a catalog expansion of Forge's
existing recovery:

- ROMs are imported exactly as before. There is no CadEditor import, project format, editor or pipeline.
- A recognized cartridge's translated layouts become a standard extraction pack that Forge's own intake
  (`ExtractionPack.open`) validates and `ResourceLibrary.register` stores. They appear in the Resource library and
  Resource Explorer like any other pack.
- Editable copies are ordinary Forge projects, built with Forge's scene constructor and `ProjectStore.prepareLoad`.
- Native profiles keep priority. A screen table Forge already recovers natively (TMNT Area 1,
  `tmnt-us-area1-blocks-v1`) is left to the native profile, and the intake still reports the native profile.
- No CadEditor code is copied. The decoders are independent implementations of the formats. None of the checkout's
  `*.bin` files (CHR, palette and RAM dumps captured from emulators) is read, copied or shipped.

## Translation

A configuration is **decodable** when its screens, blocks and (when its screens are made of big blocks) big blocks
are all stated as constants in a supported format, and nothing marks them as coming from a memory dump. Otherwise it
is **partial** (some parts translated) or **untranslated**. Every untranslated part keeps its reason, for example:
game-specific reader code, a non-constant address, a dump file, objects or layouts (a later batch).

Formats (Forge names):

| Format | What a record holds |
|---|---|
| `tiles16-attribute-byte` | 4x4 tiles, row by row, plus one attribute byte per block (four 2-bit palettes) in a parallel array |
| `linear-2x2-palette-array` | 2x2 tiles (optionally stored column by column), plus one palette byte per block in a parallel array (2 bits, at an optional shift) |
| `linear` | w x h tiles (optionally column by column), optionally followed by its palette bytes |
| `aligned-arrays-2x2` | five parallel arrays: the four quadrant tiles (optionally column by column), then palette (low 2 bits, or left to the big blocks) and type (high nibble) |
| `tiles16-attribute-interleaved` | 17-byte records: one attribute byte (four 2-bit palettes), then 4x4 tiles (Castlevania) |
| `computed-2x2` | no table: a block's four tiles are computed from its number (base + per-quadrant offsets; Mega Man 1-2, Little Samson, Banana Prince) |
| big blocks `aligned-2x2` | four parallel arrays of block IDs (TL, TR, BL, BR), optionally followed by one colour byte per big block (Tiny Toon) |
| big blocks `linear-2x2` | four block IDs (TL TR BL BR, or TL BL TR BR; optionally only the bits of a mask name the block), optionally one colour byte per big block (four 2-bit palettes) |
| screens | records of `[offset, count, size, width, height]`, byte or 16-bit cells, optional stride, optionally stored column by column |

Counts a configuration does not state take CadEditor's own default (256 blocks, 256 big blocks); a per-ID count
function is a gap.

Game-specific helpers are translated only when their whole body is a parameterised use of a shared format. The
translator strips each recognized statement and requires nothing to remain. Examples: the Ninja Gaiden helpers are
linear 2x2 blocks plus 2x2 big blocks with a colour byte; Mega Man's blocks are computed from the block number, and
its big blocks keep the block in the low 6 bits. Anything else stays untranslated with its reason.

## Recognition

1. **Exact revision.** The cartridge's SHA-256 is in the verification ledger: Agent Lab examined that revision. Each definition still carries its own evidence level.
2. **Title hint and structure.** The imported file name matches a catalog title. Sequel numbers must agree both
   ways: "Mega Man 2" is not "Mega Man". At least one decodable definition must be structurally *supported* on this
   cartridge.

A renamed file is recognized only by its exact revision. Structure alone never identifies a game. The acceptance
suite measures why: without a title hint, definitions of unrelated games pass the structural checks on some
cartridges.

**Structural applicability** of a definition on one cartridge:

- every stated range lies inside the cartridge;
- every screen cell names a valid block or big-block ID, and every big block used names a valid block;
- the blocks used are not mostly uniform, and the screens use at least four distinct IDs;
- a stated palette table holds NES colours, and a stated pattern table lies in CHR ROM.

Two measures of how surprising a pass is:

- **Analytic.** log10 P = cells × log10(share of this cartridge's PRG bytes below the ID limit).
- **Empirical control.** The same geometry is read at 99 deterministic shifted offsets of the same cartridge. If
  shifted reads pass too, the stated offset is not singled out.

| State | Meaning |
|---|---|
| `supported` | The checks pass, analytic P ≤ 1e-6, and no shifted read passes |
| `consistent` | The checks pass, but the evidence is weak. With 256 IDs, for example, every byte is valid |
| `contradicted` | A check fails |

## Evidence levels (coverage is tracked per level)

| Level | Requires |
|---|---|
| catalog | A configuration exists upstream |
| translated | The configuration is decodable by a Forge decoder |
| structurally consistent | On a local revision, the definition is `supported` or `consistent` |
| runtime-observed | On a local revision, NES Forge's emulator, running a scripted input, shows the game drawing a decoded screen |
| independently verified | FCEUX, running the same input, also shows a decoded screen of that definition |

**Observation.** Both engines capture at the same program event: the k-th entry of the game's NMI handler, every 15th. A split-screen game switches pattern tables mid-frame, so the capture point decides which table is seen. Captures read the logical nametables `$2000-$2FFF`. Matching screens accounts for
scrolling and for 32-row screens wrapping through 30-row nametables:

- each band of cell rows is located on its own, by 2x2 tile groups voting for an offset with wrap-around;
- each band is checked tile by tile, one screen width (32 columns) at a time;
- matching bands must agree on the horizontal offset;
- the screen's most common (filler) tile is not counted.

A screen counts as observed when at least 64 tiles are compared and at least 90% match. Attribute (palette) agreement
is recorded alongside.

**Graphics.** At every capture that shows a screen, the pattern table the game used for its background (from PPUCTRL)
is located:

- in CHR ROM, as 1 KiB offsets;
- for CHR RAM, by searching PRG for each tile verbatim. When every non-uniform tile is found, the table is recorded
  as runs of PRG offsets plus the uniform tiles' byte. The editor rebuilds it from the user's cartridge.

The location seen most often is kept. Graphics count as established only when the engines that saw the screens located the same ones. The editor reads graphics from the user's own cartridge at these offsets, or at
the offset the configuration states. Previews and editable copies exist only where graphics are established;
otherwise a resource carries tile numbers and palettes without pictures.

## In the editor

- **On import** (`RomImports`), a recognized cartridge's pack is built and registered. To turn this off, set
  localStorage `forge.cadport.auto` to `off`. The pack is deterministic, so a second import registers nothing new.
- **Intake report.** The row *Translated layouts (CadEditor)* states the definitions, screens, basis, and what is left
  to the native profile.
- **Commands.** `cadport.recognize`, `cadport.register`, `cadport.pack`, `cadport.coverage` and `cadport.status`.

## Limitations

- Batch 1 covers layouts only: blocks, big blocks and screens. Objects, enemies, level order, collision, the games'
  engines and audio are not part of these resources.
- Many games (558 configurations) read blocks with game-specific code. Those remain untranslated until their readers
  are re-implemented as Forge decoders, one shared format at a time.
- NES Forge's emulator does not run Battletoads past its pre-level screen with the same input: it waits in a loop at `$863E` from about frame 2,700, while FCEUX continues into Level 1. Battletoads-1 is therefore observed in FCEUX only. This is a limitation of NES Forge's emulator, recorded rather than worked around.
- Runtime observation depends on reaching an area with a scripted input. Areas a script does not reach are
  structurally checked only.
- There is no writer from translated layouts back into the original cartridge. Editable copies are Forge projects.
- Translations were checked on the local cartridges listed in the ledger. Every other game in the catalog is
  translated but untested here.
